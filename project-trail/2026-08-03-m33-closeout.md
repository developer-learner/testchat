## Root cause of the re-execution

Two accumulated-spec defects composed:

1. **DELTA-v77 is over-wide.** Its `changed_tests` lists ~50 carried UI tests
   (the byte-identical-restage workaround repopulating a spec-only delta, the
   documented M31-era pattern). The subtree invalidation correctly treats a
   task whose mapped tests appear in `changed_tests` as hit — so T2/T3/T4,
   all complete and green, were invalidated and re-executed.
2. **The plan briefs are v74 artifacts.** T4's brief mandates "install BOTH
   data.threads and data.revision into the persistence owner." The
   implementation that actually passes the frozen oracle (landed `d2661bf`,
   hand-adjusted during the CEO session) installs only the revision at
   startup. Brief and oracle disagree; the coder faithfully implemented the
   brief and the oracle rejected it — twice, plus one revision cycle.

Neither the coder nor the ladder misbehaved. The spec layer carried stale
scope and a stale implementation directive; the machinery executed them.

## Resolution (TPM authority, delegated 2026-07-27)

- `cd7f756` reverts `b1f06ce`; `53289d6` reverts `b0471ed` — app.js restored
  to the proven-green implementation. T2's `8040b54` retained: green on its
  mapped tests and the isolated pair, and reverting a passing pipeline commit
  adds churn without evidence.
- T4 escalation resolved as **spec-defect, no code change owed**: the task's
  goal state predates the run. Recorded here; state dir cleaned by close-out.
- Close-out performed manually, replicating the orchestrate success path
  exactly (fingerprint regenerated via `validate-plan.py --field fingerprint`,
  `completion-ledger.py record` at spec v77, CURRENT.md results, state
  cleanup, `[success] spec v77` commit) — per the M28 manual-close precedent
  with the full evidence table above.
